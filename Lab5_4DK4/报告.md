# Lab 5 跨层仿真：ARQ 与预约式 MAC

两条链路共用一条前向数据信道。每条链路用 ARQ 决定下一帧是新帧还是重传，用预约信道决定什么时候可以发送。仿真程序是 `src/cross_layer.c`，实验脚本是 `run_lab5.py`。

```bash
cd Lab5_4DK4
make
python3 run_lab5.py
```

单次运行的例子：

```bash
./src/cross_layer --ws 16 --wr 1 --mac sched --timer tx \
  --pd 0 --pa 0 --timeout 15 --n 0 --tend 20000
```

本报告改写了 Lab 4 的四个实验：窗口（原 Q2）、超时（原 Q5）、数据帧差错（原 Q3），以及有限长度传输的完成时间（原 Q6）。另外用短事件跟踪核对了 ARQ 和 MAC 是否接在一起。

## 1. 模型

时间单位是毫秒，帧长沿用 Lab 4。

| 量 | 取值 |
| --- | --- |
| 数据帧传输时间 \(D\) | 1 ms（1000 bit，1 Mbps） |
| 单向传播时延 \(\tau\) | 5 ms |
| ACK 传输时间 | 0 |
| ACK 信道 | 每条链路一条专用反向信道，不竞争 |
| ACK 差错 | 本报告的实验里 \(p_a = 0\) |
| 数据帧从开始发送到 ACK 回到发送端 | \(D + 2\tau = 11\) ms |
| 预约 minislot | 0.5 ms，即每个数据帧时间内 2 个 minislot |
| 预约反馈 | \(2\tau = 10\) ms：请求传到调度点，授权再传回发送端 |
| 一次成功预约 | 只换来一个数据帧的发送权，用完即失效 |

两条链路一直对称。连续积压实验里，观察窗口固定为 \(T = 20000\) ms，从 \(t = 0\) 起算，开头等预约的时间算在 \(T\) 里面。随机情形用三组种子重复：`400440917`、`400460804`、`230411341234134134`，轮换作为数据差错、ACK 差错和预约抛硬币的种子。无随机的调度、无差错情形只跑一组，结果是确定的。

序列号按整数一直增加，不取模。这样窗口行为不会和序号回绕缠在一起。

## 2. 事件和状态

全系统一个事件堆。同一时刻的顺序是：ACK、数据帧到达、超时、预约成功、预约失败、minislot。ACK 排在超时前面，所以 \(T_{out} = 11\) ms 时，刚好返回的 ACK 会先把窗口滑走，不会被当成丢失。

每条链路的帧只有四种状态：还没进入窗口、已经可以发（READY）、已经交给信道（FLY）、已经被发送端确认（ACKED）。

主要事件：

- **minislot**：有发送需求的链路按 MAC 规则决定是否发出预约。
- **GRANT / COLLISION**：预约发出 10 ms 之后，发送端知道结果。成功则得到一个发送名额。
- **数据帧开始**：名额被消耗时，ARQ 才选定序号。开始时刻是 \(\max(现在,\ 信道空闲时刻)\)，两条链路排在同一条前向信道上。
- **接收**：再过 \(D+\tau = 6\) ms。以概率 \(p_d\) 丢弃，丢弃不产生 ACK。
- **ACK**：接收端再过 \(\tau\) 送回。\(p_a = 0\) 时 ACK 不会丢。
- **超时**：见下一节。

GBN 和 S&W 的接收窗口是 1，只收按序帧，ACK 是累积的。SR 的接收窗口在窗口实验里等于 \(W_s\)，在差错和超时实验里 \(W_s = W_r = 16\)，ACK 是选择的。超时后，重传比新帧优先占用下一个名额。

发送需求 = 处于 READY 的帧数 − 尚未返回的预约 − 还没用掉的名额。因此在途帧加上已经占住的预约不会超过 \(W_s\)。

## 3. 两种 MAC

**调度基线（sched）。** 偶数 minislot 只给链路 0，奇数只给链路 1。这不是竞争，用来确认模型：没有碰撞时，吞吐应当只受窗口和数据信道限制。

**时隙 ALOHA（aloha）。** 两条链路只要还有需求，就在每个 minislot 上以 \(p = 0.5\) 独立请求。同一个 minislot 里两个请求都失败。\(p = 0.5\) 时，若两边每个时隙都想发，则该时隙恰好成功一次的概率是 \(2p(1-p) = 0.5\)。每毫秒两个 minislot，平均每毫秒成功 1 次，刚好对准数据信道每毫秒 1 帧的容量。\(p = 1\) 会让两条积压链路每次都撞在一起，仿真里效率为 0，用来确认碰撞判断没有写反。

名额不绑定序号。真正开始占信道时，ARQ 再从 READY 帧里挑最老的重传，没有重传才发新帧。这样 MAC 只负责“何时能发”，ARQ 负责“发哪一帧”。

## 4. 定时器

默认从**数据帧真正开始发送**时起算（`--timer tx`）。等预约、等前向信道空出来的时间都不在定时器里。帧还在 READY 时不会有这种超时。

对比设置是从帧**刚变成可发送**时起算（`--timer ready`）。预约往返和排队都算进 \(T_{out}\)。

等待接入期间如果超时先到了：不复制第二份帧，只把同一个定时器再武装一次。帧已经发出去之后超时：S&W / GBN 从发送窗口基序号整窗退回，SR 只重传那一帧。退回之后这些帧重新变成 READY，必须再拿一次预约才能上信道。

## 5. 指标

链路 \(i\) 的归一化吞吐是观察区间内按序交付的不同帧数乘以 \(D\)，再除以 \(T\)。共享信道效率是两条链路吞吐之和。信道占用率另算，重传也占信道，所以有差错时占用率会高于效率。

平均接入时延是帧最近一次变成 READY 到它真正开始发送的时间。其中约 10 ms 是预约的双向传播，多出来的部分是 MAC 排队，不是传播时延。

有限传输：每条链路 \(N = 100\) 帧。起点是 \(t = 0\)，两条发送端同时变为积压，初始接入等待算进去。终点是发送端处理完“本链路 \(N\) 帧都已确认”的那条 ACK。系统完成时间是两条链路终点的较大值。一条链路先完成就不再请求，剩下的信道给另一条。

## 6. 用短跟踪核对实现

S&W、调度、无差错、\(N = 3\)（`results/traces/sw_sched.log`）：

| 时刻 (ms) | 发生的事 |
| --- | --- |
| 0 / 0.5 | 链路 0、链路 1 各自在自己的 minislot 上请求 |
| 10 | 链路 0 得到授权并发送帧 0 |
| 11 | 链路 1 发送帧 0（信道被链路 0 占到 11 ms） |
| 16 / 21 | 链路 0 接收、ACK 返回 |
| 31 | 链路 0 的下一帧才发送 |

从请求到发送是 10 ms，从发送到 ACK 是 11 ms，一帧循环 21 ms。接入时延正好是 10.0 ms 和 10.5 ms，没有把传播和排队混在一起。长跑 \(T = 20000\) ms 时每条链路吞吐为 0.0476，等于 \(1/21\)。

GBN、\(W_s = 4\)、\(p_d = 0.5\) 的跟踪里，帧 0 在 10 ms 发送，16 ms 被丢弃，25 ms 超时。超时等于发送时刻加 15 ms，不是请求时刻加 15 ms。重传要再等一次授权，35 ms 才重新发送帧 0，随后按 GBN 把 1、2、3 也退回去重传。

## 7. 实验一：窗口（对应 Lab 4 Q2）

无差错，\(p_a = 0\)，\(T_{out} = 15\) ms，定时器从发送时刻起算。图在 `results/ws/`。

无差错、调度接入时，一条链路能维持的吞吐是

\[
S = \min\left(0.5,\ W_s / 21\right).
\]

21 ms 是预约反馈 10 ms 加上数据往返 11 ms。两条链路把这条管道叠在一起，但前向数据信道每毫秒只有一帧，所以每条链路最多 0.5，效率和最多是 1。\(W_s / 21 = 0.5\) 给出 \(W_s \approx 10.5\)，因此 \(W_s \ge 11\) 应当把信道填满。

仿真和这条式子一致：

| \(W_s\) | 链路 0 吞吐 | \(W_s/21\)（不超过 0.5） | 效率 | 接入时延 |
| --- | ---: | ---: | ---: | ---: |
| 1（S&W） | 0.0476 | 0.0476 | 0.0952 | 10.0 ms |
| 4 | 0.1904 | 0.1905 | 0.3808 | 10.0 ms |
| 8 | 0.3775 | 0.3810 | 0.7550 | 10.2 ms |
| 11 | 0.4996 | 0.5000 | 0.9992 | 11.0 ms |
| 16 | 0.4996 | 0.5000 | 0.9992 | 21.0 ms |
| 24 | 0.4996 | 0.5000 | 0.9992 | 37.0 ms |

效率和不是整数 1，是因为前 10 ms 还在等第一次授权。\((20000-10)/20000 = 0.9995\)，仿真是 0.9992。无差错时 GBN 和 SR 重合，因为根本没有重传。

时隙 ALOHA 在 \(W_s = 16\) 的效率是 0.954（三组种子的标准差约 0.004），低于调度的 0.999。缺口来自碰撞和两边同时沉默的空时隙，不是 ARQ。S&W 几乎看不出竞争：调度 0.0952，ALOHA 0.092。窗口为 1 时两边很少同时有需求，碰撞很少。

接入时延把传播和排队分开了。信道还没满时，时延就是预约往返，大约 10 ms。信道满了以后每条链路每 2 ms 才能发一帧，ACK 往返盖住约 \(11/2 = 5.5\) 帧，多出来的窗口都在排队：

\[
\text{接入时延} \approx 2\,(W_s - 5.5)\ \text{ms}.
\]

\(W_s = 11, 16, 24\) 分别给出 11、21、37 ms，和表里一致。把窗口开得比 11 更大，不会提高无差错吞吐，只会让帧在 MAC 里等更久。

## 8. 实验二：超时（对应 Lab 4 Q5）

图在 `results/tout/`。这一组专门看 MAC 会不会改变 \(T_{out}\) 该怎么选。

**定时器从发送时刻起算。** 无差错时，ACK 在发送后 11 ms 回到发送端。\(T_{out} = 8\) ms 会在 ACK 之前超时。调度 GBN（\(W_s = 16\)）效率掉到 0.666，但信道占用率仍约 1：信道被提前退回的重传占满。\(T_{out} \ge 11\) ms 之后效率回到 0.999，再加大超时没有好处，也没有坏处。ALOHA 的门槛同样是 11 ms，平台值是 0.954。竞争把效率压低了，但没有把“ACK 还要多久”这件事改变。接入等待发生在发送之前，不在这个定时器里面。

**定时器从帧变为可发送时起算。** 预约和排队都被算进超时。调度 GBN、\(W_s = 16\) 在 \(T_{out} = 15\) ms 时效率只有 0.019，信道却仍然是满的，每帧平均发送几十次。要到 \(T_{out} = 60\) ms 才回到 0.999。原因是饱和后的接入时延已经有 21 ms，再加上 11 ms 的数据往返，超时至少要盖住三十多毫秒；第一次把整个窗口同时放进 READY 时，队尾帧还要再等整窗串行发送，所以实际要到约 60 ms 才不再误超时。ALOHA 下这条曲线更高也更抖：碰撞把请求速率压低，误重传没有调度那么猛，但要到大约 60 ms 才和“定时器从发送起算”重合。

S&W、定时器从可发送起算、\(T_{out} < 21\) ms 是另一个结果。每帧发送次数仍是 1，效率反而高于 0.095：\(T_{out} = 15\) ms 时效率为 0.111。超时发生时帧已经在信道上，但 ACK 还没到。这一次超时去预约“重传”，ACK 却先回来把旧帧确认掉。名额不绑定序号，于是这个名额被下一帧新数据用掉，等于提前做了下一次预约。\(T_{out} \ge 25\) ms 之后这个提前量消失，效率回到 0.095。

有真实丢帧时（\(p_d = 0.1\)，定时器从发送起算），\(T_{out} = 11\) ms 最好：调度 SR 效率 0.821，调度 GBN 只有 0.447。超时加到 60 ms 时，两边都因为等一个已经丢失的帧而变慢，SR 掉到 0.417，GBN 掉到 0.213。SR 的每帧发送次数一直约 1.11，接近 \(1/(1-p_d)\)；GBN 在 2.2 以上，因为一帧丢失会把后面已经收到的帧也重传掉。

## 9. 实验三：数据帧差错（对应 Lab 4 Q3）

\(W_s = 16\)，\(T_{out} = 15\) ms，定时器从发送起算，\(p_a = 0\)。图在 `results/pd/`。

| \(p_d\) | S&W 调度 | GBN 调度 | SR 调度 | GBN ALOHA | SR ALOHA |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 0.095 | 0.999 | 0.999 | 0.954 | 0.954 |
| 0.05 | 0.089 | 0.591 | 0.866 | 0.644 | 0.838 |
| 0.10 | 0.083 | 0.406 | 0.772 | 0.473 | 0.746 |
| 0.20 | 0.073 | 0.229 | 0.633 | 0.287 | 0.613 |
| 0.50 | 0.044 | 0.061 | 0.332 | 0.094 | 0.320 |

S&W 随 \(p_d\) 下降很慢，因为它本来就几乎空着信道，丢一帧只是把 21 ms 的循环按几何分布拉长。

GBN 和 SR 在 \(p_d = 0\) 相同。一旦有丢帧，GBN 把整个窗口退回，调度时信道占用率保持在 0.999，但 \(p_d = 0.1\) 时每帧要发 2.42 次，效率只剩 0.406。SR 只重传丢失的那一帧，同样条件下每帧 1.11 次，占用率 0.859，效率 0.772。

这里能看出 MAC 和 ARQ 的交互：有丢帧时，ALOHA 的 GBN 效率高于调度的 GBN（\(p_d = 0.1\) 时 0.473 对 0.406，标准差约 0.008，差距站得住）。调度让 GBN 的退回重传几乎不间断地占满信道；碰撞反而把请求速率限住了，浪费的重传少一些。SR 不靠这种“被动限流”，它需要每一次成功预约，所以调度的 SR 仍然略高于 ALOHA（0.772 对 0.746）。竞争对一种 ARQ 是损耗，对另一种 ARQ 却顺便抑制了无效重传。

## 10. 实验四：一百帧的完成时间（对应 Lab 4 Q6）

图在 `results/finite/`。系统完成时间从 \(t = 0\) 算到两条链路都收到最后一帧 ACK。

无差错、调度时，完成时间和 21 ms 的管道一致：

| 协议 | 完成时间 | 和哪条式子相符 |
| --- | ---: | --- |
| S&W | 2101.5 ms | \(100 \times 21\) ms，链路 1 再晚 1.5 ms（minislot 相位和信道排队） |
| GBN，\(W_s = 2\) | 1054.5 ms | 大约减半 |
| GBN，\(W_s = 8\) | 283.5 ms | 窗口仍小于 11 |
| GBN，\(W_s \ge 11\) | 220.0 ms | 10 ms 第一次授权 + 200 帧数据 + 最后一帧的 ACK |

200 帧（两条链路各 100）以每毫秒一帧发送，从第一次授权的 10 ms 算起，最后一帧的 ACK 落在 220 ms。初始接入等待被算进完成时间，不是从第一帧开始发送才计时。

\(p_d = 0.05\) 时窗口不是越大越好。调度 GBN 在 \(W_s = 11\) 时约 387 ms，\(W_s = 24\) 时约 503 ms（种子标准差大约 20 到 50 ms）。窗口越大，一次丢失带回去的帧越多。SR 继续变好：调度下 \(W_s = 16\) 约 278 ms，\(W_s = 24\) 约 260 ms。ALOHA 的完成时间整体比调度长几十毫秒，种子之间的起伏也更大，但 SR 优于 GBN、S&W 最慢，这个次序在三组种子里不变。

## 11. 结果是否稳、模型缺了什么

无差错调度没有随机性，和 \(W_s/21\)、2100 ms、220 ms 这些数对得上，实现错误会先在这里暴露。ALOHA 和无差错以外的点用了三组种子。连续时间实验里，效率的种子标准差大多在 0.01 以内，调度和 ALOHA 之间、GBN 和 SR 之间的差距都大于这个起伏。有限长度、\(p_d = 0.05\) 时完成时间的标准差有几十毫秒，所以“GBN 在 \(W_s = 11\) 和 16 之间谁略好”不必看得太细，但“\(W_s = 24\) 的 GBN 比 SR 差一截”是清楚的。

没有放进模型的东西：

- 只有两条对称链路，业务要么一直积压，要么每边固定 100 帧，没有随机到达。
- ACK 传输时间为 0，这些实验里也没有 ACK 差错。反向信道被假设成专用的。
- 预约分组本身的传输时间折进 minislot，反馈固定为 \(2\tau\)，碰撞就是两个请求都作废。
- 授权不绑定序号。这使 S&W 在“过早超时”时能把名额让给下一帧；若授权写死序号，那一次名额会被取消或打成一次真正的重传。
- 观察窗口包含开头 10 ms。效率因此比稳态低大约 0.0005，表里已经按这个解释。

若再加链路，调度基线要把 minislot 按链路编号轮流分配，ALOHA 的 \(p\) 也要下降，否则碰撞会先把预约信道打满。若预约和数据改走同一条信道，minislot 和数据帧就要抢时间，10 ms 的反馈不再能和数据发送并行。若发送端改为随机到达，窗口常常填不满，实验一里的 \(W_s/21\) 平台会消失，完成时间也不再由整窗管道决定。

## 12. 结论

ARQ 和 MAC 各管一件事，但性能由两边的时间加在一起决定。预约反馈把无差错管道从 Lab 4 的 11 ms 加长到 21 ms，所以 \(W_s = 11\) 才把共享数据信道填满，而不是 \(W_s\) 只要大于 1 就够。定时器若从发送时刻起算，竞争不改变超时门槛，门槛仍是 11 ms；定时器若从“可以发了”起算，就要盖住接入时延，GBN 大窗口在调度下要大约 60 ms 才不再误重传。

有丢帧时，SR 明显好于 GBN。GBN 会把共享信道占满却传不出多少新数据；适度的预约碰撞反而少做了一些无效退回。无差错时则相反，碰撞只是在浪费本可以拿满的信道。把两种协议接在一起之后，多出来的难点主要是：超时的起点、授权和序号要不要绑在一起，以及一个还在等信道的帧超时之后不能再复制一份。
